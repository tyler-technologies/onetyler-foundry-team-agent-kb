## How to Update Identity Configuration for a Domain Change

### Simple Overview
When a customer's domain changes, the redirect URIs (the URLs where users return after logging in) need to be updated to match the new domain. This ensures authentication can complete successfully.

---

### Step-by-Step Process

#### **Option 1: Using Credential Templates (Recommended for Products)**
If the product uses Credential Templates, update the redirect URIs in the template configuration:

1. **Update the template file** (`<filename>.clients.yaml`):
   - Modify the `redirectUris` and `postLogoutRedirectUris` fields with the new domain
   - Templates support Handlebars syntax for dynamic values: `{{domain}}/callback`

2. **Apply the updated template** using the Provisioning SDK:
   ```csharp
   await credentialTemplateClient.ApplyTemplateAsync(
       new ApplyTemplateContext {
           RegistrationId = "your-product-id",
           TemplateVersion = "version",
           TcpEnvKey = "production",
           WorkspaceKey = "customer-workspace",
           Variables = new() {
               { "domain", "https://newdomain.com" }
           }
       });
   ```

#### **Option 2: Direct Update via Client Operations API**
For direct credential management, use the `/client_operations` endpoint:

**Request:**
```json
POST /client_operations
Content-Type: application/json

{
  "operation_type": "update_redirects",
  "client_id": "your-client-id",
  "operations_token": "your-operations-token",
  "redirect_uris": [
    "https://newdomain.com/signin-callback",
    "https://newdomain.com/other-callback"
  ],
  "post_logout_redirect_uris": [
    "https://newdomain.com/signout-callback"
  ]
}
```

**Important:** The redirect URI lists must be **comprehensive** — any existing redirects not included will be removed.

---

### Technical Details

**What needs to be updated:**
- **Sign-In Redirect URIs** — Where users land after successful authentication
- **Sign-Out Redirect URIs** — Where users land after logout
- Both must match **exactly** (protocol, domain, port, path)
- Production must use HTTPS (localhost can use HTTP for development)

**Operations Token Management:**
- Each request consumes the operations token
- A new token is returned with each successful response
- Store and use the latest token for subsequent operations

For more details, see the [Credential Templates documentation](https://docs.tylerdev.io/identity) in the Blueprint docs.
