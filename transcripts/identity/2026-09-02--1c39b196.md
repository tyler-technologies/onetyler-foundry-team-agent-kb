Great questions! Let me help you understand how TID can integrate with FusionAuth and address each of your scoping questions.

## **Quick Overview**

Tyler Identity (TID) Gateway acts as an identity federation router that sits between your applications and identity providers. It supports **both SAML 2.0 and OIDC** protocols for federation, giving you flexibility in how you integrate FusionAuth.

---

## **Detailed Answers to Your Questions**

### **1. SSO Protocols Supported**

**TID supports:**
- ✅ **OIDC (OpenID Connect)** - preferred protocol
- ✅ **SAML 2.0** - fully supported

For federation with third-party IdPs like FusionAuth, TID Gateway can federate using **either OIDC or SAML 2.0**. Your CloudGavel application would integrate with TID Gateway using **OIDC** (this is required), while the Gateway handles the federation to FusionAuth using whichever protocol FusionAuth supports.

**Technical details:**
- Gateway exposes standard OIDC discovery at `{authority}/.well-known/openid-configuration`
- Common endpoints: `/oauth2/authorize`, `/oauth2/token`, `/oauth2/userinfo`, `/oauth2/v1/keys`, `/oauth2/v1/logout`

📖 [Identity Workforce Configuration](https://docs.tylerdev.io/identity)

---

### **2. Architecture & Roles**

Based on your current setup (CloudGavel → TID Gateway → IdP), here are the integration options:

**Option A: FusionAuth as the Customer IdP (Recommended)**
```
CloudGavel → TID Gateway → FusionAuth (as customer IdP)
```
- FusionAuth acts as the **Identity Provider (IdP)**
- TID Gateway acts as the **Service Provider (SP)** / broker
- CloudGavel remains the **Relying Party**
- Routing happens via `organizationKey` or domain

**Option B: FusionAuth as a Broker**
```
CloudGavel → TID Gateway → FusionAuth → Other IdPs
```
- FusionAuth acts as an **intermediary broker**
- Allows FusionAuth to aggregate multiple downstream IdPs

**Technical Requirements for FusionAuth (as IdP):**
- Must be externally accessible from public internet
- Must support either OIDC or SAML2 protocols
- Must be highly redundant and scalable
- Should be from a trusted industry vendor (FusionAuth ✅)

---

### **3. Claims, Attributes & Identity Linking**

**Required Claims/Attributes:**
TID Gateway requires these standard attributes from the federated IdP:

| Required | Claim/Attribute | Description |
|----------|----------------|-------------|
| ✅ | Email | User's email address |
| ✅ | Username | User's unique username |
| ✅ | First Name | Given name |
| ✅ | Last Name | Family name/surname |

**Claims TID Gateway Issues (what CloudGavel receives):**

**In ID Token:**
- `sub` - Subject (unique user identifier)
- `preferred_username` - Username
- `organizationKey` / `home_org` - Organization identifier
- `workspaceKey` - Workspace context (if provided)
- Standard claims: `iss`, `aud`, `exp`, `iat`, `auth_time`

**In Access Token:**
- Context scopes: `org:<organizationKey>` and `wks:<workspaceKey>`
- `amr` (Authentication Methods References)
- `acr` (Authentication Context Class Reference)

**Identity Linking Strategy:**
Recommended user matching flow:
1. Check if `sub` matches user's sub in application → Update profile
2. If no match, check if username + organizationKey match → Link and update
3. If no match, trigger JIT (Just-In-Time) provisioning for new users

📖 [Token Examples & Claims Documentation](https://docs.tylerdev.io/identity)

---

### **4. MFA, Session Lifetime & Logout**

**MFA / Step-Up Authentication:**
- TID Gateway supports **AMR (Authentication Methods References) passthrough**
- The `acr` claim indicates authentication strength:
  - `urn:tidg:password` - Password only
  - `urn:tidg:mfa` - Multi-factor authentication
  - `urn:tidg:aal2` - NIST AAL2 compliant factors
- MFA is enforced at the **FusionAuth level**, not TID Gateway
- Gateway passes through authentication context from FusionAuth

**Session Lifetime:**
- **Access tokens**: Maximum 60 minutes
- **ID tokens**: Typically 5 minutes
- **Refresh tokens**: Typically 90 days (requires `offline_access` scope)
- **Authorization codes**: 5 minutes

**Logout Behavior:**
- ✅ **Single Logout (SLO)**: Gateway supports federated logout
- ⚠️ **Important**: Not all IdPs support federated logout (e.g., Google Workspace doesn't)
- **Back-channel logout**: Contact Identity team for current support status
- **Front-channel logout**: Use the `/oauth2/v1/logout` endpoint with `post_logout_redirect_uri`

**Logout Flow Consideration:**
```
User clicks logout → Gateway logout → FusionAuth session may persist
→ User auto-logs back in if they revisit
```

**Solution**: Redirect to a public page after Gateway logout, or set user expectations that browser closure may be needed for complete logout.

---

### **5. Environments, Certificates & Metadata**

**TID Gateway Environments:**

| Environment | Gateway Authority | Use Case |
|-------------|------------------|----------|
| **Dev** | `https://idgw.tcpci.com/tg` | Development & testing |
| **QA** | `https://idgw.tcpqa.com/tg` | Quality assurance |
| **Prod** | `https://idgw.tylerportico.com/tg` | Production |

**Metadata Exchange:**
- **For SAML**: Upload FusionAuth IdP metadata XML to Admin Center
- **For OIDC**: Configure FusionAuth discovery endpoint in Admin Center
- Admin Center is where IdP configuration is managed per organization

**Certificate/Keys Management:**
- **JWKS (JSON Web Key Set)** published at: `{authority}/.well-known/openid-configuration/jwks`
- Applications validate JWT signatures using JWKS
- JWKS are automatically cached by most libraries (~24 hours)

**Rotation Requirements:**
- TID Gateway supports **client secret rotation**
- Grace period of **3 days** when rotating secrets
- Use `client_operations` endpoint for managed rotation

**Client Registration per Environment:**
You'll need separate client registrations for each environment (Dev, QA, Prod).

---

### **6. Risks, Open Questions & Recommendations**

**✅ Recommended Approach:**

1. **Use OIDC over SAML** if FusionAuth supports both (simpler, more modern)
2. **FusionAuth as Customer IdP** (Option A) - cleaner architecture
3. **Implement PKCE** for Authorization Code Flow (security best practice)
4. **Plan JIT user provisioning** with proper identity linking strategy
5. **Test with multiple organizations** (`tylertownwa` tenant in prod is required for operational testing)

**⚠️ Risks to Consider:**

| Risk | Mitigation |
|------|-----------|
| **Logout loop issues** | Redirect to public page after logout; don't require auth on landing page |
| **Session persistence** | FusionAuth sessions may persist after Gateway logout |
| **Certificate expiration** | Monitor FusionAuth IdP certificate validity; update metadata in Admin Center |
| **Token validation overhead** | Implement JWKS caching; avoid excessive introspection calls |
| **MFA bypass** | Ensure FusionAuth enforces MFA policies; validate `acr` claims in CloudGavel |

**🔍 Open Questions to Clarify:**

1. **Does FusionAuth support OIDC or SAML or both?** (Determines federation protocol)
2. **Will FusionAuth manage multiple downstream IdPs?** (Determines if it's an IdP or broker)
3. **What MFA capabilities does FusionAuth have?** (Determines AMR/ACR claim mapping)
4. **How many organizations/tenants need FusionAuth integration?** (Impacts configuration approach)
5. **Is this multi-tenant CloudGavel or single-tenant per customer?** (Impacts client registration strategy)
