## Quick Summary

**TID does NOT provide automatic JIT (Just-In-Time) provisioning capabilities.** The TID Gateway is focused on **authentication and federation**, not user provisioning. **CloudGavel is responsible for creating and managing its own user accounts** based on the identity information provided in tokens after successful authentication.

## Detailed Answers to Your Questions

### 1. **What is JIT Provisioning in the Context of TID?**

In standard identity systems, JIT provisioning means automatically creating a user account in an application when someone successfully authenticates for the first time. However, **TID Gateway does not provide this functionality**. 

The Gateway's role is:
- **Authentication** through external IdPs
- **Token issuance** with user claims
- **IdP routing** based on organizationKey
- **Session management**

**User provisioning is the responsibility of each Tyler application**, including CloudGavel.

### 2. **Does TID Create Users Automatically?**

**No.** TID Gateway does not create users in CloudGavel or any other application. After successful authentication, the Gateway issues tokens containing user claims, but **CloudGavel must implement its own logic** to:
- Check if the user exists
- Create a new user if needed
- Update existing user information
- Handle access control

### 3. **What Information Does TID Provide for User Creation?**

After successful authentication, TID Gateway provides user information through **JWT tokens** (ID token and access token) with the following standard claims:

**Key Claims Available:**
- **`sub`**: Subject - a **unique, immutable identifier** for the user from the IdP
- **`preferred_username`**: Username of the user
- **`email`**: Email address
- **`given_name`**: First name
- **`family_name`**: Last name
- **`home_org`** (or `organizationKey`): The customer organization identifier
- **Additional custom claims** from the customer's IdP (if configured)

The customer's IdP can be configured through Admin Center to map additional SAML attributes or OIDC claims.

According to the [tyler-identity-knowledge-base.md](/api/tenant-knowledge-base/collections/TCP-KB-Identity/files/01546ed8-be5a-4cf1-ba40-0ab86a8c7dc9/download), the Gateway requires these attributes to be configured: "Check required SAML attributes/OIDC claims are configured (Email, Username, First name/Last name)."

### 4. **Can CloudGavel Map Attributes from External IdPs?**

**Yes**, but CloudGavel must extract these from the token claims and perform the mapping itself. The workflow is:

1. User authenticates through TID Gateway → External IdP
2. External IdP returns user attributes to Gateway
3. Gateway issues tokens with claims
4. **CloudGavel receives tokens and extracts claims**
5. **CloudGavel maps claims to its user model**
6. **CloudGavel creates or updates the user record**

### 5. **Does TID Support User Updates After First Login?**

**No built-in JIT updates.** However, CloudGavel can:

**Option A: Extract updated attributes from tokens on each login**
- Parse the latest claims from the ID token
- Update the CloudGavel user record with current information
- This is essentially "CloudGavel-implemented JIT updates"

**Option B: Subscribe to Identity Events** (for Workforce Direct organizations only)

TID provides **asynchronous events** that CloudGavel can subscribe to:

According to [tyler-identity-knowledge-base.md](/api/tenant-knowledge-base/collections/TCP-KB-Identity/files/01546ed8-be5a-4cf1-ba40-0ab86a8c7dc9/download):

- **`workforce-user-created`**: New user created
- **`workforce-user-disabled`**: User disabled
- **`workforce-user-enabled`**: User enabled
- **`workforce-user-profile-changed`**: User attributes modified (includes old values)
- **`workforce-user-deleted`**: User removed
- **`user-added-to-group`**: User added to a group
- **`user-removed-from-group`**: User removed from a group

**Important limitation**: "Workforce events are only published for Organizations that are using **Workforce Direct**" (not for organizations using their own external IdPs).

### 6. **How is User Deactivation Handled?**

**TID Gateway does not automatically prevent disabled users from attempting to access CloudGavel.** The behavior depends on where the user is disabled:

**Scenario A: User disabled in external IdP**
- The external IdP will **deny authentication**
- User cannot complete login flow
- CloudGavel never receives a token
- **Result**: User is effectively blocked

**Scenario B: User disabled in Admin Center (Workforce Direct only)**
- A `workforce-user-disabled` event is published
- CloudGavel can subscribe to this event and disable the user locally
- On next login attempt, the user may still authenticate at the IdP, but CloudGavel should check local account status

**Recommendation**: CloudGavel should implement both:
1. Real-time checks during login (verify user is not disabled locally)
2. Event subscriptions to stay synchronized with identity changes

## Identity Migration Scenario: Okta → Azure/Entra ID

This is a **challenging scenario** that TID does not natively solve. Let me explain what's possible and what's not.

### 7. **Does TID Support Identity Correlation/Mapping Across Different Identifiers?**

**No.** TID Gateway does not provide identity correlation or linking when the user's identifier changes between IdPs.

The Gateway:
- Routes authentication requests to the correct IdP based on `organizationKey`
- Issues tokens with claims from the authenticating IdP
- Does **not** maintain any cross-IdP identity mapping

### 8. **Your Desired Flow - Is It Supported?**

The flow you described:
> CloudGavel sends: `abc@gmail.com` → TID determines Azure tenant → Azure authenticates using `[REDACTED-EMAIL]` → TID maps back to `abc@gmail.com`

**This is NOT supported by TID.** Here's why:

1. **TID does not accept user identifiers from applications** during the authorization request
2. **TID routes based on `organizationKey`**, not user email
3. **TID does not maintain user identity mappings**
4. The `organizationKey` determines which IdP to use—there's only one IdP per organization

### 9. **Does TID Support Tenant/Home Realm Discovery?**

**No**, not in the way you're describing. 

The Gateway uses **`organizationKey`** for routing, which CloudGavel must provide in the authorization request. According to [tyler-identity-knowledge-base.md](/api/tenant-knowledge-base/collections/TCP-KB-Identity/files/01546ed8-be5a-4cf1-ba40-0ab86a8c7dc9/download):

> "**IdP Routing**: Routes authentication requests based on `organizationKey` parameter or global domain registration"

**CloudGavel must already know** which organization the user belongs to before initiating authentication. TID does not discover this based on email address.

### 10. **Can TID Provide a Stable, Immutable User Identifier?**

**Yes!** This is the **`sub` claim** (Subject).

From [tyler-identity-knowledge-base.md](/api/tenant-knowledge-base/collections/TCP-KB-Identity/files/01546ed8-be5a-4cf1-ba40-0ab86a8c7dc9/download):

> "`sub`: Subject — unique identifier for the authenticated user"

**This is critical for your use case.** Instead of using email as the user key, **CloudGavel should use the `sub` claim** as the primary identifier.

**However**, there's a problem: **the `sub` value will likely change when the IdP changes** from Okta to Azure/Entra ID because:
- Okta generates its own `sub` values
- Azure/Entra ID generates different `sub` values
- These are issued by different identity providers

## Recommended Architecture for IdP Migration

Since TID doesn't support identity correlation, **CloudGavel must implement this logic**. Here's the recommended approach:

### **Phase 1: Preparation (Before Migration)**

1. **Store multiple identifiers** for each CloudGavel user:
   - `primary_sub`: Current sub from Okta
   - `email`: Current email
   - `username`: Current username
   - `organization_key`: Organization identifier

2. **Create a migration mapping table** with:
   - Old Okta identifier (email: `abc@gmail.com`)
   - New Azure identifier (email: `[REDACTED-EMAIL]`)
   - CloudGavel user ID

3. **Coordinate with customer** to obtain the identity mapping

### **Phase 2: Migration Cutover**

1. **Customer changes IdP configuration** in Admin Center from Okta to Azure/Entra ID

2. **CloudGavel implements flexible user matching logic**:

```
On authentication callback:
  1. Extract claims from ID token (sub, email, preferred_username, organizationKey)
  2. Try to find user by: sub + organizationKey (exact match)
  3. If not found, check migration mapping table by email + organizationKey
  4. If found in mapping:
     - Update user record with new sub from Azure
     - Update email if changed
     - Log successful migration match
  5. If still not found, consult on-boarding policy (create new or deny)
  6. Continue authentication flow
```

### **Phase 3: Post-Migration**

1. **Gradually remove old identifiers** after all users have logged in at least once
2. **Monitor unmigrated accounts** and assist users
3. **Use the `sub` claim** as the primary stable identifier going forward

### **Key Points for Identity Continuity**

✅ **Use `sub` claim as primary key** (but be aware it changes with IdP)  
✅ **CloudGavel must implement identity correlation logic**  
✅ **Maintain a migration mapping during transition**  
✅ **Subscribe to identity events** (if using Workforce Direct)  
✅ **Update user attributes from token claims on each login**  
⚠️ **TID does not provide automatic linking or JIT provisioning**  
⚠️ **TID routes by `organizationKey`, not by user email**

def resolve_organization_and_agency(id_token_claims):
    """
    Determine CloudGavel organization and agency from TID claims.
    """
    org_key = id_token_claims['organizationKey']
    email = id_token_claims['email']
    email_domain = email.split('@')[1] if '@' in email else None
    
    # Step 1: Find or create CloudGavel organization
    cg_org = db.query("""
        SELECT * FROM cloudgavel_organizations 
        WHERE tid_organization_key = ?
    """, [org_key])
    
    if not cg_org:
        # Auto-provision organization
        cg_org_id = db.execute("""
            INSERT INTO cloudgavel_organizations (tid_organization_key, name, created_at)
            VALUES (?, ?, NOW())
        """, [org_key, org_key])  # Could fetch name from Ops Center API
        cg_org = get_organization(cg_org_id)
    
    # Step 2: Determine agency
    # Option A: Email domain-based routing
    if email_domain:
        agency = db.query("""
            SELECT * FROM cloudgavel_agencies 
            WHERE organization_id = ? AND email_domain = ?
        """, [cg_org.id, email_domain])
        
        if agency:
            return cg_org, agency
    
    # Option B: Check if user already has agency assignment
    user = get_user_by_tid_sub(id_token_claims['sub'], org_key)
    if user:
        primary_agency = db.query("""
            SELECT a.* FROM cloudgavel_agencies a
            JOIN user_agency_assignments uaa ON a.id = uaa.agency_id
            WHERE uaa.user_id = ? AND uaa.is_primary = TRUE
        """, [user.id])
        
        if primary_agency:
            return cg_org, primary_agency
    
    # Option C: Let user select (return organization only)
    return cg_org, None  # Agency selection required

## 4. Can Email Domain Be Used for Agency Resolution?

### **✅ Yes, But With Caveats**

**Email domain can be a reasonable starting point, but it's not foolproof.**

### **Pros of Email Domain Routing:**

✅ Simple to implement  
✅ Works for organizations where each agency has distinct domains  
✅ No additional TID configuration required  
✅ Automatic agency detection  

### **Cons of Email Domain Routing:**

❌ Not reliable if multiple agencies share same domain (`user@government.com`)  
❌ Email can change during IdP migrations  
❌ Users may have multiple email addresses  
❌ External users (contractors) may have non-agency domains  
❌ No standardization across government agencies  

### **Recommended Hybrid Approach:**

```
1. Try email domain lookup
     ↓
   Found single agency? → Assign automatically
     ↓
   Found multiple agencies or none?
     ↓
2. Check user's previous agency assignments
     ↓
   Found? → Use existing assignment
     ↓
   Not found?
     ↓
3. Check for TID group membership (if events available)
     ↓
   Found group-to-agency mapping? → Assign based on group
     ↓
   Still no match?
     ↓
4. Prompt user to select agency
     ↓
   Store selection as user's primary agency
```

### **Implementation:**

```python
def smart_agency_resolution(user, organization_id, email):
    """
    Multi-strategy agency resolution.
    """
    email_domain = extract_domain(email)
    
    # Strategy 1: Exact domain match
    agencies = db.query("""
        SELECT * FROM cloudgavel_agencies 
        WHERE organization_id = ? AND email_domain = ?
    """, [organization_id, email_domain])
    
    if len(agencies) == 1:
        # Unambiguous match - assign automatically
        assign_user_to_agency(user.id, agencies[0].id, is_primary=True)
        log_info(f"Auto-assigned user {user.id} to agency {agencies[0].name} based on domain {email_domain}")
        return agencies[0]
    
    # Strategy 2: User already has assignment
    existing_agency = get_user_primary_agency(user.id)
    if existing_agency and existing_agency.organization_id == organization_id:
        return existing_agency
    
    # Strategy 3: Check TID group membership (if using events)
    # (This would be populated from user-added-to-group events)
    tid_groups = get_user_tid_groups(user.id, organization_id)
    if tid_groups:
        for group in tid_groups:
            agency = db.query("""
                SELECT a.* FROM cloudgavel_agencies a
                JOIN agency_tid_group_mappings m ON a.id = m.agency_id
                WHERE m.tid_group_name = ? AND a.organization_id = ?
            """, [group.name, organization_id])
            
            if agency:
                assign_user_to_agency(user.id, agency.id, is_primary=True)
                return agency
    
    # Strategy 4: If multiple agencies match domain, let user choose
    if len(agencies) > 1:
        # Store available options in session
        store_agency_options(user.id, agencies)
        return None  # Triggers UI selection
    
    # Strategy 5: No matches - show all agencies for org
    all_agencies = db.query("""
        SELECT * FROM cloudgavel_agencies 
        WHERE organization_id = ?
    """, [organization_id])
    
    store_agency_options(user.id, all_agencies)
    return None  # Triggers UI selection
```
