## **6. Security: Tenant Enumeration**

You're absolutely right that **unauthenticated email → org resolution is a tenant-enumeration risk**.

The documentation **does not provide specific guidance** on how to safely implement domain-to-org lookup for unauthenticated users.

**General security considerations:**
- The Gateway itself doesn't expose org enumeration (you send organizationKey, not discover it)
- If CloudGavel implements domain lookup client-side or via an unauthenticated API, you create the enumeration surface
- Rate limiting and monitoring would be your responsibility

**Potential mitigations:**
- Keep the domain mapping table internal (server-side only)
- Use rate limiting on any lookup endpoint
- Consider requiring some form of intent verification (CAPTCHA, email verification link with embedded org context)
- Log all lookup attempts for abuse detection
- Consider whether partial-trust scenarios (like org picker with known org names) are acceptable

**TID doesn't expose** an unauthenticated "email → org" lookup API that I can find in the documentation, likely for exactly this reason.

## **Why Domain Mapping Breaks Down**

### **Real-world scenarios where domains collide:**

1. **Multiple departments in the same government:**
   - Austin Police Department → `@austintexas.gov`
   - Austin Fire Department → `@austintexas.gov`

3. **Consolidated IT services:**
   - Entire state of Washington IT → `@wa.gov`
   - Department of Licensing uses CloudGavel → `@wa.gov`
   - Department of Revenue also uses CloudGavel → `@wa.gov`

4. **Personal email addresses:**
   - Small agencies without dedicated domains
   - Users with `@gmail.com`, `@outlook.com`, etc.
   - **Completely unresolvable** via domain

**Domain → Org mapping is 1:many, not 1:1.** This makes pure domain-based routing **impossible** for many real deployments.

---

## **What This Means for Your Architecture**

You have **three scenarios** to handle:

### **Scenario A: Domain maps to exactly ONE organization**
- `judge.smith@smallcity.gov` → Only one CloudGavel org uses this domain
- **Domain lookup works**

### **Scenario B: Domain maps to MULTIPLE organizations**
- `officer.jones@austintexas.gov` → Could be Police, Fire, Parks, etc.
- **Domain lookup is ambiguous — you MUST disambiguate**

### **Scenario C: Domain maps to ZERO organizations**
- `john.doe@gmail.com` → No CloudGavel org registered this domain
- **Domain lookup fails — user must identify themselves another way**

---

Given these constraints, here are your **actual options**:

**Flow:**

  ↓
  ├─ One match found? → Auto-redirect with organizationKey
  ├─ Multiple matches found? → Show picker:
  │    "Which department are you with?"
  │    • Austin Police Department
  │    • Austin Fire Department  
  │    • Austin Parks & Recreation
  └─ Zero matches? → "Email not recognized" or generic org picker
```

**Database schema:**
```sql
CREATE TABLE organization_domains (
  id INT PRIMARY KEY,
  organization_key VARCHAR(255),  -- e.g., "austin-police"
  organization_name VARCHAR(255),  -- e.g., "Austin Police Department"
  email_domain VARCHAR(255),       -- e.g., "austintexas.gov"
  is_primary BOOLEAN,              -- Hint for default selection
  UNIQUE(organization_key, email_domain)
);

-- Example data:
-- org_key: austin-police, domain: austintexas.gov
-- org_key: austin-fire,   domain: austintexas.gov
-- org_key: austin-parks,  domain: austintexas.gov
```

  ○ Austin Police Department
  ○ Austin Fire Department
  ○ Austin Parks & Recreation
  [Sign In]

Step 3: Redirect to Gateway with correct organizationKey
```

**Advantages:**
- Handles all three scenarios (1:1, 1:many, 0:many)
- User only sees picker when necessary
- No enumeration risk (only shows orgs for entered domain)

**Disadvantages:**
- Extra step for users in multi-org domains

## **Database Schema (Realistic Model)**

Given this complexity, here's what your schema actually needs to look like:

```sql
-- Organizations
CREATE TABLE organizations (
  organization_key VARCHAR(255) PRIMARY KEY,  -- e.g., "austin-police"
  organization_name VARCHAR(255),              -- e.g., "Austin Police Department"
  subdomain VARCHAR(255) UNIQUE,              -- e.g., "austin-police" for austin-police.cloudgavel.com
  created_at TIMESTAMP,
  active BOOLEAN DEFAULT TRUE
);

-- Email domains that are ALLOWED for each organization
-- (many-to-many relationship)
CREATE TABLE organization_allowed_domains (
  id INT PRIMARY KEY AUTO_INCREMENT,
  organization_key VARCHAR(255) REFERENCES organizations(organization_key),
  email_domain VARCHAR(255),                   -- e.g., "austintexas.gov", "gmail.com"
  is_primary BOOLEAN DEFAULT FALSE,           -- Hint for display ordering
  added_by VARCHAR(255),                       -- Who registered this domain
  added_at TIMESTAMP,
  UNIQUE(organization_key, email_domain),
  INDEX(email_domain)                          -- Critical for lookup performance
);

-- User → Organization membership history
-- (tracks which users have authenticated to which orgs)
CREATE TABLE user_organization_history (
  id INT PRIMARY KEY AUTO_INCREMENT,
  email VARCHAR(255),
  organization_key VARCHAR(255) REFERENCES organizations(organization_key),
  first_login_at TIMESTAMP,
  last_login_at TIMESTAMP,
  login_count INT DEFAULT 0,
  UNIQUE(email, organization_key),
  INDEX(email),                                -- Critical for lookup
  INDEX(last_login_at)                         -- For "recently used" sorting
);

-- Actual CloudGavel users (created on JIT)
CREATE TABLE users (
  id INT PRIMARY KEY AUTO_INCREMENT,
  sub VARCHAR(255) UNIQUE,                     -- From OIDC token (stable identifier)
  email VARCHAR(255),
  organization_key VARCHAR(255) REFERENCES organizations(organization_key),
  username VARCHAR(255),
  first_name VARCHAR(255),
  last_name VARCHAR(255),
  created_at TIMESTAMP,
  last_authenticated_at TIMESTAMP,
  UNIQUE(email, organization_key)              -- User might exist in multiple orgs
);
