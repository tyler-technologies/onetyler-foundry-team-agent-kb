## Simple Answer

**The TID Gateway handles authentication only, not user provisioning.** When a user from an external IdP authenticates, TID federates that authentication and issues tokens. TID does not maintain a persistent user database or automatically sync lifecycle changes from external IdPs.

**For lifecycle synchronization, you should use Workforce Direct Events.**

---

## Detailed Technical Architecture

### 1. **What mechanism does TID use to receive user lifecycle changes?**

**TID Gateway itself does NOT directly receive lifecycle changes from external IdPs.** The Gateway is a federation broker focused on authentication, not a user directory.

However, for organizations using **Workforce Direct**, TID publishes **Platform Events** when user lifecycle changes occur:

- `workforce-user-created`
- `workforce-user-disabled`
- `workforce-user-enabled`
- `workforce-user-profile-changed`
- `workforce-user-deleted`

These events are published **only for organizations using Workforce Direct** (not for all external IdP integrations).

[Reference: Identity Events Overview](https://docs.tylerdev.io/identity)

### 2. **Does TID support SCIM or other provisioning standards?**

**No.** Based on the documentation, TID Gateway does not support:
- SCIM (System for Cross-domain Identity Management)
- Direct API-based provisioning from external IdPs
- Webhook-based synchronization from customer IdPs

The architecture relies on:
- **Federation for authentication** (SAML/OIDC from customer IdP → TID Gateway)
- **Events for lifecycle synchronization** (Workforce Direct → Platform Events)

### 3. **Does TID maintain a representation of externally managed users?**

**Limited representation.** The TID Gateway:
- Does **NOT** maintain a comprehensive user directory
- Does **NOT** store user profiles from external IdPs
- **DOES** include basic user claims in tokens (from IdP assertions):
  - `sub` (subject identifier)
  - `preferred_username`
  - `email`
  - `given_name`, `family_name`
  - `organizationKey`

**Important:** The documentation explicitly states:
> "The Gateway does not support custom claim mapping or claim extensions. Applications that need custom claims should retrieve them from their own data stores or **use Platform Events to synchronize user data**."

### 4. **How is lifecycle information exposed to downstream products?**

Through **Platform Events**. Products like CloudGavel should:

1. **Subscribe to Workforce Events** via the Platform Event system
2. **Implement event handlers** for:
   - `workforce-user-created` → Create local user record
   - `workforce-user-disabled` → Disable/revoke access
   - `workforce-user-profile-changed` → Update profile attributes
   - `workforce-user-deleted` → Remove or archive user

**Example Event Payload (User Disabled):**
```json
{
  "messageType": "workforce-user-disabled",
  "sub": "5xieRMfpq3ha7Z8PjIoTD8tS",
  "organizationKey": "mycivicid",
  "username": "test.two@mycivicid.com",
  "givenName": "Test",
  "familyName": "Two",
  "email": "test.two@mycivicid.com"
}
```

[Reference: Identity Events Example Payloads](https://docs.tylerdev.io/identity)

### 5. **Is there an API or provisioning interface for products?**

**No direct provisioning API.** Instead:

- Products should **subscribe to Platform Events** for asynchronous user synchronization
- Products should implement **Just-in-Time (JIT) provisioning** on first login

**Recommended JIT Flow from documentation:**
> When a user logs in:
> 1. Does the `sub` match the user's sub in application? → Yes: Update profile and username from ID token
> 2. No: Does the username match a username and organizationKey in the application? → Yes: Update User sub in application, then update profile
> 3. No: Does the application have an on-board process for new users?

### 6. **How should deprovisioning work?**

**Multi-layered approach:**

**Layer 1: Authentication (Real-time)**
- When a user is disabled in external IdP, they **cannot authenticate** through TID Gateway
- Existing tokens remain valid until expiration (max 60 minutes for access tokens)
- No new tokens can be issued

**Layer 2: Event-Based Sync (Asynchronous)**
- CloudGavel subscribes to `workforce-user-disabled` event
- On receiving event, CloudGavel:
  - Marks user as inactive in local database
  - Revokes active sessions (if applicable)
  - Prevents access even with valid tokens

**Layer 3: Token Validation (Per-Request)**
- CloudGavel APIs should validate:
  - Token signature and expiration
  - User's active status in local database
  - `organizationKey` claim matches expected tenant

### 7. **What is the source of truth?**

**Customer's External IdP** is the source of truth for:
- User authentication credentials
- User active/disabled status
- Basic profile attributes (name, email)

**Workforce Direct** acts as the **synchronization mechanism** that:
- Monitors changes in the customer's IdP (for Workforce Direct organizations)
- Publishes events to the Platform Event system
- Enables Tyler products to maintain synchronized copies

**Tyler Products (like CloudGavel)** maintain:
- Local user records synchronized via events
- Product-specific authorization/roles
- Product-specific user data

## Key Limitations & Gaps

1. **Events only for Workforce Direct**: Organizations NOT using Workforce Direct will not publish lifecycle events
2. **No real-time deprovisioning**: Token expiration (up to 60 minutes) means disabled users may have temporary access
3. **No group synchronization**: Group memberships are NOT included in tokens or events
4. **Manual initial setup**: Products must implement their own JIT provisioning logic

---

## Next Steps for CloudGavel

1. **Subscribe to Platform Events** for the four key lifecycle events
2. **Implement JIT provisioning** on first login (based on token claims)
3. **Validate tokens on every API request** and check local user status
4. **Consider token revocation** strategies for immediate deprovisioning needs
5. **Coordinate with Workforce Direct team** to ensure customer organizations are properly configured

For subscribing to events, you'll need to obtain an identity client credential and register your event subscriptions through the Platform Event system.
