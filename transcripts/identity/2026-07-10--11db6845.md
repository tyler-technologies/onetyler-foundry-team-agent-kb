**Q:**

> How do I configure multiple identity providers?

**A:**

```markdown
Based on the information available, here's how to configure multiple identity providers:

## Simple Answer

The Identity Gateway automatically handles multiple identity providers for you. Each customer organization can have their own IdP (like Microsoft Entra ID, Google Workspace, or Ping Identity) configured in **Admin Center**. When users authenticate, the Gateway routes them to the correct IdP based on the `organizationKey` parameter you pass in your authorization request.

## How It Works

The Identity Gateway acts as a **federation router** that sits between your Tyler application and multiple customer IdPs. Here's the flow:

1. Your application sends users to the Gateway with an `organizationKey` parameter
2. The Gateway looks up which IdP is configured for that organization
3. The Gateway routes the user to their organization's IdP for authentication
4. After authentication, the Gateway issues tokens back to your application

## Configuration Requirements

**For Customer IdPs to be configured, they must:**
- Be externally accessible from the public internet
- Support either **OIDC** or **SAML 2.0** protocols
- Be highly redundant and scalable
- Be from a trusted industry vendor

**Supported IdP Examples:**
- Microsoft Entra ID (formerly Azure AD)
- Ping Identity
- Rapid Identity
- Duo SSO
- Google Workspace
- OneLogin
- Thales SafeNet Trusted Access
- ForgeRock

## Technical Details

**IdP Configuration is managed through Admin Center** where:
- IdP metadata (XML file or URL) is uploaded for SAML providers
- OIDC connection details are configured for OIDC providers
- Required claims/attributes are mapped (Email, Username, First name, Last name)

**In your authorization request**, include the organization identifier:
```http
GET {authority}/oauth2/authorize?
  client_id=your_client_id
  &organizationKey=customer_org_key
  &redirect_uri=your_redirect_uri
  &response_type=code
  &scope=openid profile email
```

The Gateway handles all the complexity of federating with different IdP protocols - your application only needs to integrate with the Gateway using standard OIDC.

For more details, see the Identity Workforce documentation at https://docs.tylerdev.io/identity
```

**Q:**

> What scopes do I need for an identity client

**A:**

```markdown
## Simple Answer

For an identity client, you need these **minimum required scopes**:

- `openid` - Required for OIDC authentication
- `profile` - Returns user profile information (name, etc.)
- `email` - Returns the user's email address

**Optional scope:**
- `offline_access` - Returns a refresh token (use this if you need long-lived sessions)

## Scope Strategy

The recommended approach for scopes depends on your use case:

**For User Authentication (Authorization Code Flow):**
```
openid profile email offline_access
```

**For Service-to-Service Communication (Client Credentials Flow):**
- Define at least **1 product-specific scope** (e.g., `yourproduct.api`)
- Or use the platform scope: **`tyler-cloud-platform-api-access`** for Tyler Cloud Platform API calls

## Technical Details

### Standard Scopes Breakdown

| Scope | Description | Required |
|-------|-------------|----------|
| `openid` | Indicates OIDC flow, returns ID token | Yes |
| `profile` | Returns profile claims (name, etc.) | Yes |
| `email` | Returns email claim | Yes |
| `offline_access` | Returns refresh token | Optional |

### When Registering Your Client

When you submit an Identity Client Service Desk ticket or create a Credentials Template, you'll specify:
- **Scopes**: `openid profile email` (minimum required)
- Additional scopes based on your needs

### Example Authorization Request

```http
GET {authority}/oauth2/authorize?
  client_id=your_client_id
  &scope=openid profile email offline_access
  &response_type=code
  &redirect_uri=your_redirect_uri
  &organizationKey=customer_org_key
```

### Important Notes

- **No custom scopes in tokens**: The Gateway does not support custom claim mapping or claim extensions
- **No group scopes**: Group information is not available via a `groups` scope
- **Product-specific scopes**: Recommended for API authorization and access control

For more details, see the Identity Workforce documentation at https://docs.tylerdev.io/identity
```

**Q:**

> Tell me about client credential flow

**A:**

```markdown
## What is Client Credentials Flow (CCF)?

**Client Credentials Flow** is an OAuth 2.0 authentication method for **service-to-service communication** where no user is involved. Your application uses its client ID and secret to obtain an access token directly from the Identity Gateway.

Think of it as a "service account" - your application authenticates as itself, not on behalf of a user.

## When to Use CCF

**Use Client Credentials Flow for:**
- Backend API to API communication
- Scheduled jobs and batch processes
- Service accounts (applications acting on their own behalf)
- System-to-system integration

**Do NOT use CCF for:**
- User-facing authentication (use Authorization Code Flow instead)
- Scenarios where you need user identity or `organizationKey` context

## If You Don't Want to Use CCF

If you don't need service-to-service communication, **you don't have to use CCF at all**. Instead, use:

**Authorization Code Flow (with PKCE)** for user authentication:
- This is for when actual users log in to your application
- Users authenticate through their organization's IdP
- You get user identity information and organizational context
- This is the primary flow for most Tyler applications

## Technical Details

### How CCF Works

**Request an access token:**
```http
POST https://idgw.tcpci.com/tg/oauth2/token
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials
&client_id={your_ccf_client_id}
&client_secret={your_ccf_client_secret}
&scope={your_api_scope}
```

**Response:**
```json
{
  "access_token": "eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "scope": "your-api-scope"
}
```

### Important Limitations of CCF

- **No user context**: CCF tokens do NOT contain `organizationKey`, `preferred_username`, or other user-specific claims
- **Token lifetime**: Access tokens are valid for 1 hour
- **Scope strategy**: Use product-specific scopes (e.g., `yourproduct.api`) or the platform scope `tyler-cloud-platform-api-access`

### How Many CCF Clients Do You Need?

1. **Multi-tenant cloud product**: Only need a single CCF client per product
2. **Cloud product deployed per customer**: Need a CCF client per customer and/or environment
3. **On-premise**: Recommend a client per product per environment

### C# Example

```csharp
public async Task<string> GetAccessTokenAsync(string scope)
{
    var requestBody = new FormUrlEncodedContent(new[] {
        new KeyValuePair<string, string>("grant_type", "client_credentials"),
        new KeyValuePair<string, string>("client_id", _clientId),
        new KeyValuePair<string, string>("client_secret", _clientSecret),
        new KeyValuePair<string, string>("scope", scope)
    });
    
    var response = await _httpClient.PostAsync($"{_authority}/oauth2/token", requestBody);
    response.EnsureSuccessStatusCode();
    
    var content = await response.Content.ReadAsStringAsync();
    var tokenResponse = JsonSerializer.Deserialize<TokenResponse>(content);
    return tokenResponse.AccessToken;
}
```

## Summary

- **CCF is optional** - only use it if you need service-to-service communication without user context
- For user authentication, use **Authorization Code Flow with PKCE**
- CCF tokens don't have user or organization information
- Request CCF clients through the Service Desk if you need them

For more details, see https://docs.tylerdev.io/identity
```

**Q:**

> Do I need a separate client for CCF and user authentication with gateway?

**A:**

```markdown
## Simple Answer

**Yes, you need separate clients** for CCF and user authentication. They serve different purposes and have different configurations:

1. **User Authentication Client** (LoginPKCE or LoginACF) - for users logging in
2. **Service Client** (ServiceCCF) - for service-to-service communication

You cannot use the same client for both flows.

## Why Separate Clients?

**User Authentication Client (LoginPKCE/LoginACF):**
- Used for Authorization Code Flow
- Requires redirect URIs and post-logout redirect URIs
- Returns user identity information
- Scopes: `openid profile email offline_access`

**Service Client (ServiceCCF):**
- Used for Client Credentials Flow
- No redirect URIs needed (no user interaction)
- Returns access tokens without user context
- Scopes: Product-specific scopes or `tyler-cloud-platform-api-access`

## How Many Clients Do You Need?

### For User Authentication:
**Normally, you only need a single identity client per environment** for user authentication. The Gateway supports wildcard redirects like:
- `*.tylerportico.com/portal/enterpriselauncher`
- `*.tylerportico.com/notify/*`
- `hub.tylerapp.com/*`

### For CCF (Service-to-Service):
1. **Multi-tenant cloud product**: Only need a single CCF client per product
2. **Cloud product deployed per customer**: Need a CCF client per customer and/or environment
3. **On-premise**: Recommend a client per product per environment

## Technical Details

### Client Types Available

When creating a Credential Template or requesting clients, you specify the `clientType`:

- **`LoginPKCE`** — Authorization Code Flow with PKCE (recommended for user auth)
- **`LoginACF`** — Authorization Code Flow with client secret
- **`ServiceCCF`** — Client Credentials Flow (for service-to-service)

### Example Credential Template with Both

```yaml
registrationId: your-product
version: 1.0.0
clients:
  - name: UserAuthClient
    clientType: LoginPKCE
    scopes:
      - openid
      - profile
      - email
      - offline_access
    redirectUris:
      - https://yourapp.com/callback
    postLogoutRedirectUris:
      - https://yourapp.com/logout
      
  - name: ServiceClient
    clientType: ServiceCCF
    scopes:
      - yourproduct.api
      - tyler-cloud-platform-api-access
```

## Summary

- **Yes, you need separate clients** - one for user login, one for service-to-service
- User auth clients have redirect URIs; CCF clients don't
- User auth clients return user identity; CCF clients don't
- Request both through Service Desk or include both in your Credential Template

For more details, see https://docs.tylerdev.io/identity
```
